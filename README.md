# LungPrometheus

**LungPrometheus** — сервис для хранения, просмотра и анализа КТ-исследований легких.

Система приведена к общей backend-архитектуре: REST API работает на FastAPI, данные хранятся в PostgreSQL через SQLAlchemy ORM, задачи анализа отправляются в очередь сообщений Redis и дополнительно фиксируются в PostgreSQL, чтобы после падения сервиса их можно было восстановить.

## Возможности

- регистрация и авторизация пользователей;
- тестовый аккаунт `admin` / `admin`;
- тестовое пополнение баланса;
- списание 80 ₽ за новый запрос пациента;
- **карточки пациентов**: исследования группируются по пациенту (ФИО + дата рождения) в одну карточку с историей всех его исследований, а не в плоский список;
- **загрузка «файл → карточка»**: сначала загружается файл (срез сразу открывается для предпросмотра), затем по кнопке «Добавить исследование» заполняется карточка пациента;
- **обнаружение дублей**: если ФИО и дата рождения совпадают с уже существующим пациентом (без учёта регистра/пробелов), система предлагает добавить исследование в существующую карточку вместо создания нового пациента;
- добавление нового исследования прямо из карточки пациента (кнопка «+ Добавить исследование»);
- поиск по пациентам (ФИО, ID, дата рождения) и постраничный вывод в списке пациентов;
- загрузка DICOM, серии DICOM, `.mhd + .raw` и папок исследований — файлом, папкой или перетаскиванием (drag-and-drop);
- просмотр срезов и масштабирование изображения;
- автоматическое обнаружение подозрительного объекта моделью `Improved3DCNN`;
- отображение вероятности патологии, рассчитанной моделью;
- **полноэкранная анимация анализа**: пока модель обрабатывает срезы, поверх интерфейса показывается чёрный оверлей с прокруткой среза КТ и пульсирующей подписью, в стиле «thinking»-индикатора ChatGPT;
- **тёмный монохромный интерфейс** в стиле ChatGPT (чёрный фон, светлый акцент вместо синего) вместо прежней светлой темы;
- ручное добавление находок;
- история запросов с удалением записей;
- генерация заключения через отдельный FastAPI report-сервис и Ollama, с явной пометкой источника заключения (ИИ или резервный шаблон);
- пароли хранятся хэшированными через bcrypt, ограничение частоты попыток входа, выход из системы с инвалидацией токена на сервере.

## Архитектура

```text
Browser
  |
  | REST + static files
  v
FastAPI app: backend/server.py
  |
  | SQLAlchemy ORM
  v
PostgreSQL
  |
  | durable job state
  v
Redis message queue -> model workers -> findings/reports
```

Основные компоненты:

- `backend/server.py` — FastAPI REST API и раздача фронтенда из `public/`;
- `backend/storage.py` — SQLAlchemy ORM модели (включая `PatientORM` — карточки пациентов) и слой доступа к PostgreSQL;
- `backend/slice_store.py` — хранение загруженных срезов (пиксельных данных) на диске, по одному сжатому файлу на исследование;
- `backend/workers.py` — очередь сообщений Redis с локальным fallback для тестов и фоновые воркеры, которые прогоняют сохранённые срезы через реальную модель;
- `backend/model_adapter.py` — загрузка checkpoint `Improved3DCNN` и расчет вероятности;
- `backend/report_service.py` — отдельный FastAPI-сервис генерации заключений через Ollama;
- `backend/rate_limiter.py` — потокобезопасный sliding-window rate limiter (используется для входа);
- `public/` — браузерный интерфейс.

## Безопасность

- **Пароли**: хэшируются через `bcrypt` (`backend/storage.hash_password`). Аккаунты, созданные до перехода на bcrypt, хранят пароль в старом формате `sha256$salt$digest` — он по-прежнему проверяется (`verify_password`), но при следующем успешном входе прозрачно перехэшируется в bcrypt (`needs_rehash` + `authenticate_user`), так что существующие пользователи (включая тестовый `admin`/`admin`) не теряют доступ.
- **Ограничение частоты входа**: `POST /api/auth/login` ограничен через `RateLimiter` (по умолчанию 5 неудачных попыток в минуту на пару IP+логин); при превышении возвращается `429 Too Many Requests` с заголовком `Retry-After`. Состояние хранится в памяти процесса.
- **Выход из системы**: `POST /api/auth/logout` инвалидирует токен на сервере (перегенерирует `auth_token` в БД), а не только удаляет его на клиенте — старый токен перестаёт работать сразу.
- **CORS**: вместо `allow_origins=["*"]` — явный список через `CORS_ALLOWED_ORIGINS` (через запятую). Фронтенд раздаётся тем же FastAPI-приложением (см. `StaticFiles` в `server.py`), поэтому обычная работа через браузер идёт same-origin и CORS вообще не участвует; список по умолчанию (`http://127.0.0.1:8765`, `:8775` и их `localhost`-варианты) покрывает локальный запуск и прямые обращения к API.
- **Логирование**: настроено через стандартный `logging` (`backend/server.py` вызывает `logging.basicConfig` при импорте, все `backend.*`-логгеры используют единый формат с таймстампом). Ошибки воркера (`backend/workers.py`) логируются с полным traceback (`logger.exception`) и не теряются молча; на уровне API добавлен catch-all обработчик необработанных исключений, который логирует их и возвращает JSON `500` вместо HTML-страницы ошибки FastAPI по умолчанию. Уровень регулируется переменной `LOG_LEVEL` (по умолчанию `INFO`).

## Надежность очереди

При создании задачи анализа запись сначала сохраняется в таблице `analysis_jobs`, затем идентификатор задачи отправляется в Redis. При старте воркеры поднимают задачи со статусом `queued` или `running` обратно в очередь, поэтому падение процесса не теряет уже созданные запросы.

В Docker Redis запускается с `appendonly yes`, чтобы очередь была устойчивее к перезапускам контейнера.

Срезы, отправленные вместе с запросом на анализ (`POST /api/studies/{id}/analyze`), сохраняются на диске через `SliceStore` **до** постановки задачи в очередь — поэтому воркер анализирует те же пиксельные данные, что видел пользователь при загрузке, а не заглушку. Путь для хранения задаётся переменной `STUDY_FILES_DIR` (по умолчанию `data/studies/` рядом с проектом, в Docker — `/app/data/studies` на отдельном volume). Те же срезы отдаются через `GET /api/studies/{id}/slices`, поэтому историю исследования можно открыть повторно и увидеть исходный снимок, а не только текстовые находки.

## Пациенты (карточки и миграция)

Исследования (`studies`) связаны с карточкой пациента (`patients`) через колонку `studies.patient_record_id`. При первом запуске на существующей базе `Storage.migrate()` добавляет эту колонку и один раз выполняет backfill: все ранее созданные исследования группируются по паре (пользователь, ФИО без учёта регистра/пробелов, дата рождения) и превращаются в карточки пациентов задним числом — история не теряется при обновлении. Обнаружение дублей (`POST /api/patients/match`) использует то же сравнение без учёта регистра/пробелов; исследование считается потенциальным дублем, только если совпадают **и** ФИО, **и** дата рождения — одного ФИО недостаточно, чтобы не путать однофамильцев. Удаление карточки пациента (`DELETE /api/patients/{id}`) не удаляет её исследования — они просто отвязываются (`patient_record_id` становится `NULL`) и остаются доступны через `/api/studies/{id}`.

## Модель

Checkpoint `improved_3dcnn_checkpoint.pth` подключен как файл:

```text
backend/weights/improved_3dcnn_checkpoint.pth
```

По умолчанию сервис читает его из `MODEL_WEIGHTS_PATH=/app/backend/weights/improved_3dcnn_checkpoint.pth`. Модель использует сохраненный в checkpoint `patch_size=32`, возвращает вероятность положительного класса и показывает ее в интерфейсе.

### Пороги вероятности (threshold)

В checkpoint сохранен `threshold=0.45` — это **patch-level** порог, подобранный при обучении на валидации с одним кандидатом на строку (по F1/F2, см. `HW_56.ipynb`). Он читается в `model_adapter.py` (`self.checkpoint_threshold`) и **только отображается** в метаданных ответа (`checkpointThreshold`) — на фильтрацию находок он не влияет.

Находки на реальном скане отбираются по отдельному **scan-level** порогу `MODEL_DETECTION_THRESHOLD=0.85` (по умолчанию, задаётся переменной окружения). Он строже не просто так: при анализе целого КТ модель прогоняется по десяткам-сотням кандидатных патчей на один скан (см. `NoduleModel._generate_candidates`), а не по одному кандидату, как на валидации при обучении. Порог 0.45, отобранный для одиночного предсказания, при таком переборе давал бы значительно больше ложных срабатываний на весь скан — поэтому для продакшена подобран более строгий порог. Это не баг и не рассинхронизация — метаданные checkpoint (0.45) и рабочий порог (0.85) намеренно разделены и решают разные задачи.

Если нужно пересчитать сам scan-level порог на реальных данных (а не подбирать вручную) — для этого нужен доступ к исходному датасету LUNA16 (`.mhd/.raw`, `annotations.csv`, `candidates_V2.csv`), которого нет в этом репозитории.

### Производительность генерации кандидатов

`NoduleModel._generate_candidates` перебирает объём скана в поисках кандидатных патчей, а `_build_lung_masks` для каждого среза отделяет "внутренний" воздух (лёгкие) от воздуха снаружи тела. Обе стадии раньше были реализованы построчными Python-циклами — на полноразмерном КТ (сотни срезов, 512×512) это доминировало во времени анализа: на синтетическом скане 260×512×512 полный проход занимал около **60 секунд**, из них **58 секунд** — заливка (flood fill) для отделения внутреннего воздуха от внешнего.

Обе стадии переписаны на векторизованные операции с тем же результатом (проверено тестами на точное совпадение с прежней реализацией, поэлементно):

- `_edge_connected_mask` — раньше ручной BFS на `collections.deque`, теперь `scipy.ndimage.label` (компоненты связности с 4-связностью, как и раньше) с последующим отбором компонент, касающихся границы кадра.
- `_mask_fraction_near` (вызывался по одному разу на каждую точку сетки кандидатов) — заменён на `_box_mean_grid`, который считает то же самое (среднее по обрезанному по границам окну) для всей сетки сразу через integral image (summed-area table).

На том же синтетическом скане полный `_generate_candidates` теперь укладывается примерно в **4 секунды** (~15× быстрее), при этом находит идентичный набор кандидатов.

## REST API

| Метод | URL | Назначение |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка сервиса |
| `GET` | `/api/stats` | Статистика |
| `POST` | `/api/auth/register` | Регистрация |
| `POST` | `/api/auth/login` | Вход (ограничен по частоте, см. раздел «Безопасность») |
| `POST` | `/api/auth/logout` | Выход, инвалидирует токен на сервере |
| `GET` | `/api/auth/me` | Текущий пользователь |
| `POST` | `/api/balance/top-up` | Тестовое пополнение баланса |
| `POST` | `/api/patients/match` | Проверить, есть ли уже пациент с таким ФИО + датой рождения (для диалога «добавить в карту или создать нового») |
| `GET` | `/api/patients` | Список карточек пациентов пользователя, с поиском (`?query=`) |
| `POST` | `/api/patients` | Создать карточку пациента (без списания средств) |
| `GET` | `/api/patients/{id}` | Получить карточку пациента вместе со всеми его исследованиями |
| `DELETE` | `/api/patients/{id}` | Удалить карточку пациента (исследования не удаляются, только отвязываются от карточки) |
| `POST` | `/api/patients/{id}/studies` | Добавить новое исследование в карточку пациента, списывает 80 ₽ |
| `GET` | `/api/studies` | История исследований пользователя (плоский список, для обратной совместимости) |
| `POST` | `/api/studies` | Создать запрос пациента напрямую (без карточки), списывает 80 ₽ — оставлен для обратной совместимости |
| `GET` | `/api/studies/{id}` | Получить исследование |
| `DELETE` | `/api/studies/{id}` | Удалить исследование |
| `POST` | `/api/studies/{id}/findings` | Добавить находку |
| `POST` | `/api/studies/{id}/analyze` | Сохранить срезы и поставить реальный анализ моделью в очередь |
| `GET` | `/api/studies/{id}/slices` | Получить сохранённые срезы исследования (для повторного просмотра) |
| `GET` | `/api/jobs/{id}` | Проверить статус задачи |
| `POST` | `/api/viewer/analyze` | Синхронно прогнать модель по срезам без сохранения (использовалось UI раньше) |
| `POST` | `/api/reports/generate` | Создать заключение; ответ содержит `source` (`ollama` или `fallback`) — какой механизм фактически сгенерировал текст |

## Быстрый старт

```bash
docker compose up --build
```

После запуска интерфейс доступен по адресу:

```text
http://127.0.0.1:8765
```

PostgreSQL доступен на `127.0.0.1:5432`, Redis — на `127.0.0.1:6379`.

## Локальный запуск API

Для запуска без Docker нужен доступный PostgreSQL и переменная `DATABASE_URL`:

```bash
export DATABASE_URL="postgresql+psycopg://lung:lung@127.0.0.1:5432/lung_prometheus"
export REDIS_URL="redis://127.0.0.1:6379/0"
python3 backend/server.py
```

Report-сервис можно запустить отдельно:

```bash
uvicorn backend.report_service:app --host 127.0.0.1 --port 8766
```

Если Ollama недоступна, report-сервис использует резервный шаблон заключения.

## Пример API

Вход:

```bash
curl -X POST http://127.0.0.1:8765/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin"}'
```

Пополнение баланса:

```bash
curl -X POST http://127.0.0.1:8765/api/balance/top-up \
  -H "Content-Type: application/json" \
  -H "X-Auth-Token: TOKEN" \
  -d '{"amount":800}'
```

Создание запроса пациента:

```bash
curl -X POST http://127.0.0.1:8765/api/studies \
  -H "Content-Type: application/json" \
  -H "X-Auth-Token: TOKEN" \
  -d '{"patient_name":"Иван Петров","birth_date":"1980-01-02","description":"КТ грудной клетки"}'
```
